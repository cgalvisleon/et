¿Cómo guarda et/store tus datos?

Un recorrido por el paquete store/ de la librería et: un almacén clave-valor de un solo nodo hecho sobre un log de solo anexar con un índice en memoria. Es pequeño (unas 3.300 líneas de Go), así que se puede entender de punta a punta, y usa muchas de las ideas que vimos en PostgreSQL y CockroachDB.

1. La vista general

store guarda pares id → []byte. No entiende de tablas, columnas ni JSON: solo bytes con un nombre. Nació como el motor de josefina y hoy vive en et para que cualquier servicio lo use.

Toda su idea cabe en tres frases:

  • Cada escritura se agrega al final de un archivo (el log). Nunca se modifica nada que ya esté escrito.
  • Un índice en memoria recuerda, para cada id, dónde está su última versión dentro del log.
  • De vez en cuando, la compactación reescribe solo lo vigente y tira lo viejo.
Analogía: el cuaderno y el índiceTienes un cuaderno donde solo escribes en la siguiente línea libre, nunca borras. Cuando cambias el teléfono de Ana, escribes una línea nueva "Ana: 555-1234". En una tarjeta aparte (el índice) anotas "Ana → página 3, línea 12". Para buscar a Ana no lees el cuaderno: miras la tarjeta y vas directo. Cuando el cuaderno se llena de líneas tachadas, copias solo las vigentes a un cuaderno nuevo (compactación).

2. La API en un vistazo

Toda la API pública está en store/catalog.go:

s, err := store.Open("./data", "./wal", "usuarios", store.ReadWrite)
defer s.Close()

ok, err := s.Insert("u1", []byte(`{"name":"Ana"}`))   // solo si "u1" NO existe
ok, err  = s.Update("u1", []byte(`{"name":"Ana M"}`)) // solo si existe y el valor cambió
ok, err  = s.Delete("u1")                              // solo si existe

data, found, err := s.Get("u1")
data, version, found, err := s.GetVersion("u1")         // version = LSN del último registro

s.ForEach(func(id string, data []byte) (bool, error) { // en orden de clave
    return true, nil                                    // false = detenerse
}, true, 0, 100)                                        // asc, offset, limit

Hay un ejemplo completo y ejecutable en cmd/store/main.go. Muestra también los casos que devuelven false, las escrituras diferidas, la concurrencia optimista, el hook Sync y Compact:

go run ./cmd/store              # en un directorio temporal que se borra al terminar
go run ./cmd/store -dir ./data  # conserva los archivos para mirarlos
No hay upsert, a propósitoInsert falla en silencio (false) si ya existe y Update si no existe. Para "guardar sí o sí": Update; si dio false, Insert; y si el insert perdió una carrera contra otro hilo, Update otra vez. Así cada operación tiene un significado preciso, que es lo que necesita la replicación.

3. Los archivos en disco

Open(pathData, pathWald, name, mode) recibe dos raíces: una para los datos y otra para los archivos auxiliares. Con name = "usuarios":

pathData/
└── segments/usuarios/
    ├── segment-000001.dat     ← sellado (solo lectura)
    ├── segment-000002.dat     ← sellado
    └── segment-000003.dat     ← activo: aquí se agrega
pathWald/
├── snapshot/usuarios/state-usuarios.snap   ← índice guardado (opcional)
├── compact/usuarios/                       ← temporal de la compactación
└── recover/usuarios/                       ← bytes corruptos puestos en cuarentena

El nombre pasa por Normalize: espacios a _, solo letras, números, _ y ., y sin dígitos al inicio, para que sea un nombre de archivo seguro.

4. El formato de un registro

Cada operación escribe un registro en el segmento activo. Todos los números van en big-endian:

CampoPara qué sirve
LSNNúmero de secuencia creciente de cada escritura. Ordena los cambios, es la "versión" que da GetVersion y lo que usa la replicación.
DataLenCuántos bytes de datos siguen: permite saltar al siguiente registro sin leer este.
CRCHuella de los datos. Si no coincide al leer, el registro está corrupto.
IDLen + IDEl nombre de la clave. Al leer se compara con el id pedido: protege contra un índice que apunte mal.
StatusActive = 1 (guarda datos) o Deleted = 2 (tombstone).

El encabezado y los datos se escriben en una sola llamada write, para que nunca quede uno sin el otro por culpa del código (un corte de luz sí puede dejarlo a medias; lo vemos en la sección 11).

5. Segmentos

El log no es un solo archivo gigante: se parte en segmentos. Cuando el siguiente registro no cabe en el activo (tamaño RELSEG_SIZE, 128 MB por defecto), el store:

  • Sella el segmento activo: fsync y lo marca de solo lectura.
  • Crea segment-00000N+1.dat y lo vuelve el activo.
  • Guarda un snapshot del índice (sección 10).

Lectura por mmap

Los segmentos se mapean en memoria (mmap): leer un registro es copiar bytes de la memoria, sin una llamada al sistema por cada lectura. El activo se mapea con capacidad para MaxSegment bytes y un contador visible marca hasta dónde ya se escribió: nunca se lee más allá de visible. Si no se puede mapear, se usa ReadAt normal.

Ciclo de vida: acquire, release, retire

Un segmento puede quedar obsoleto (tras una compactación o al cerrar) mientras alguien lo está leyendo. Para no cerrarle el archivo en la cara:

  • acquire(): el lector se anota antes de leer; release(): se borra al terminar.
  • retire(): el store lo da de baja, pero el archivo se cierra cuando sale el último lector.

6. El índice en memoria

Para cada id vivo, el índice guarda un recordRef:

type recordRef struct {
    segment int     // en qué segmento
    offset  int64   // en qué byte empieza el registro
    length  uint32  // cuántos bytes de datos
    crc     uint32  // CRC de los datos (si hasCRC)
    hasCRC  bool    // false si vino del snapshot
}

Es un mapa partido en 64 fragmentos (shardedIndex), elegidos por un hash del id. Cada fragmento tiene su propio lock, así que una escritura bloquea solo 1/64 del índice y no a todos los lectores.

El precio del índice en memoriaTodas las claves deben caber en RAM (los datos no: esos están en disco). Y como un mapa no tiene orden, Keys y ForEach ordenan todas las claves en cada llamada (O(n log n)): bien para miles o cientos de miles de claves, caro para muchos millones.

7. Escribir y el group commit

Así recorre Update("u1", datos) el código (store.go: update, commit.go):

  • Toma writeMu: una sola escritura a la vez.
  • Busca u1 en el índice. Si no existe, retorna false.
  • Compara el largo y el CRC nuevos con los del índice. Si difieren, el dato cambió, sin leer el disco. Si coinciden, lee el valor viejo y compara byte a byte: si es igual, retorna false y no escribe nada.
  • Asigna el siguiente LSN y agrega el registro al segmento activo (rotando si no cabe).
  • Apunta el índice al registro nuevo. El viejo queda obsoleto: TombStones++.
  • Avisa a los hooks de Sync (replicación) con el cambio y su LSN.
  • Suelta writeMu. Desde aquí el cambio ya es visible para los lectores.
  • Espera el fsync y retorna true: el cambio es durable.

Group commit: un fsync para muchos

fsync (obligar al disco a guardar de verdad) es lo más lento de una escritura. Por eso se hace después de soltar writeMu:

OpciónQué hace
SYNC_ON_WRITE=true (defecto)Cada Insert/Update/Delete retorna cuando ya es durable.
s.Deferred().Insert(...)Escribe y retorna sin esperar el fsync. Para lotes: muchas escrituras diferidas y al final s.WaitDurable() una vez.
SYNC_ON_WRITE=falseNunca espera fsync. Rápido, pero un corte de luz puede perder lo último escrito.

8. Leer

Get("u1") es corto (store.go: get):

  • Con el lock de lectura del índice: busca el recordRef y hace acquire() del segmento.
  • Suelta el lock: la lectura del disco se hace sin bloquear a nadie.
  • Lee el registro entero (encabezado + id + datos) en una sola lectura, normalmente desde el mmap.
  • Verifica que el id coincida, que el status sea Active, que el largo cuadre y que el CRC sea correcto. Si algo falla: error de registro corrupto.
  • release() del segmento y retorna los datos.

GetVersion además devuelve el LSN del registro. Sirve para concurrencia optimista: lees con versión 41, modificas y, antes de guardar, compruebas que siga siendo 41; si cambió, alguien escribió en medio.

ForEach toma las claves ordenadas y las lee en paralelo (hasta NumCPU goroutines), pero entrega los resultados a tu función de uno en uno y en orden, sin locks tomados: tu función puede usar el store.

9. Compactación

Cada Update o Delete deja un registro viejo inútil en el log (lo cuenta TombStones). Cuando superan el 10% de las claves (y al menos MIN_THRESHOLD_COMPACT, 1.000 por defecto), se lanza una compactación en segundo plano. También se puede llamar Compact() a mano.

Lo interesante es que no detiene las escrituras mientras copia. Trabaja en tres fases (compact.go):

El intercambio final usa dos renombres de directorio:

segments/usuarios               →  segments/usuarios.segments.old
compact/.../segments-usuarios.tmp  →  segments/usuarios
borrar usuarios.segments.old

Si el proceso muere entre los dos renombres, el siguiente Open lo detecta (repairCompaction): si falta el directorio pero existe .old, lo restaura; si existen ambos, el intercambio terminó y borra .old.

Un detalle finoSi el registro más reciente del log era un tombstone, la compactación lo conserva. Sin él, el LSN más alto del log nuevo sería menor y, al reabrir, el contador de LSN retrocedería: dos escrituras distintas podrían tener el mismo número.

10. Snapshot: abrir rápido

Sin ayuda, Open tendría que leer todos los segmentos para reconstruir el índice. El snapshot lo evita: al rotar de segmento (y tras compactar) se guarda el índice de los segmentos sellados en state-<name>.snap:

"SNAP" | versión (2) | cantidad | LSN máximo | entradas (id, segmento, offset, largo)... | CRC
  • Se escribe en un .tmp, se hace fsync y se renombra encima del anterior: el cambio es atómico.
  • Al abrir: si el snapshot existe y su CRC es válido, se carga y solo se recorre el segmento activo. Si no existe o está dañado, se recorren todos. El snapshot es una optimización, nunca la fuente de verdad.
  • Las entradas del snapshot no traen CRC (hasCRC = false): el primer Update de esas claves lee el valor viejo para comparar.

11. ¿Qué pasa si se va la luz?

Un corte a mitad de una escritura puede dejar el final del segmento activo con un registro cortado. Los sellados no: la rotación hace fsync antes de crear el siguiente. Al abrir en ReadWrite:

  • repairCompaction deja los directorios como antes o como después de una compactación interrumpida.
  • Se reconstruye el índice recorriendo los registros. El recorrido (scan) se detiene en el primer registro inválido: largo imposible, datos incompletos o CRC que no coincide.
  • repairTail: si hay bytes después del último registro válido, los copia a recover/ (cuarentena) y trunca el segmento ahí. Así lo nuevo queda pegado a lo válido y no detrás de la basura.

Para casos peores existe store.Recover(pathData, pathWald, name), con el store cerrado: repara la compactación, borra el snapshot y revisa cada segmento, truncando y poniendo en cuarentena lo que no sea válido. Devuelve un reporte en JSON. Nunca borra nada sin dejar copia.

La garantíaLo que Insert/Update/Delete confirmó (con SYNC_ON_WRITE) ya pasó por fsync y sobrevive. Lo que estaba a medio escribir se descarta limpiamente, y queda guardado en recover/ por si hay que examinarlo.

12. Replicación

store es de un solo nodo, pero trae lo necesario para que otra capa replique (como hacía josefina):

PiezaQué hace
Sync(fn)Llama a fn(Change{Op, ID, Data, LSN}) por cada cambio aplicado, bajo writeMu: llegan exactamente en orden de LSN. Por eso fn debe ser rápida y no escribir en el store.
WalSince(lsn)Devuelve los registros con LSN mayor que lsn, en orden: lo que le falta a una réplica que se quedó atrás.
ApplyWalEntry(entry)En la réplica: aplica una entrada conservando el LSN del líder, así ambos nodos tienen las mismas versiones.
Límite aceptadoLa compactación descarta los tombstones. Si una réplica está tan atrasada que necesita un borrado anterior al corte, WalSince ya no lo tiene: esa réplica necesita una copia completa.

13. Concurrencia y locks

Las reglas que hacen seguro al store, sacadas del código:

compactMu  →  writeMu  →  indexMu  →  fragmentos del índice (en orden ascendente)
  • Orden fijo de locks: siempre se toman en ese orden, así nunca hay dos hilos esperándose mutuamente (deadlock).
  • writeMu: una escritura a la vez. Verificar, agregar al log y actualizar el índice ocurren en un mismo tramo bajo el lock: nada se cuela en medio.
  • indexMu se toma en modo compartido para buscar y en exclusivo solo para cambiar la lista de segmentos (rotar, compactar, cerrar).
  • Los lectores nunca hacen I/O con indexMu tomado: buscan, hacen acquire, sueltan y leen.
  • Los contadores compartidos (WAL, Size, TombStones…) son counter[T] atómicos, sin lock.

Visible antes que durable: al soltar writeMu el cambio ya se ve, aunque el fsync no haya terminado. Otro hilo puede leerlo una fracción de milisegundo antes de que sea durable. Es la misma decisión que toman muchos motores a cambio del group commit.

TransaccionesSí, SERIALIZABLE opcionalLotes atómicosNo: cada operación por separado

Este diseño (log + índice de claves en RAM) es el de Bitcask, el motor de Riak. Sus ventajas son la sencillez, las escrituras secuenciales y que leer cuesta siempre una lectura al disco.

Límites, según el propio código

  • Un escritor a la vez (writeMu). El group commit compensa el fsync, pero no hay escrituras en paralelo.
  • Todas las claves en RAM, y Keys/ForEach ordenan todo en cada llamada.
  • Sin transacciones de varias claves ni MVCC: un lector ve cada clave en su último estado.
  • La compactación borra los tombstones: una réplica muy atrasada necesita copia completa.
  • Sin tests en el repositorio; se prueba con segmentos pequeños, SYNC_ON_WRITE=false y -race (ver CLAUDE.md de et).
