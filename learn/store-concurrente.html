Propuesta: un store con escritura y lectura concurrentes

Cómo podría evolucionar et/store —un almacén de pares id → []byte— para que varias escrituras avancen a la vez sin perder lo que hoy lo hace confiable: semántica exacta de Insert/Update/Delete, LSN en orden, recuperación tras una caída y el mismo formato en disco. Es un diseño basado en técnicas conocidas (reserva de espacio en el log, marca de agua, locks por clave, group commit), no código probado.

1. Dónde está el cuello de botella hoy

En el store actual, las lecturas ya son concurrentes: el índice está en 64 fragmentos, los segmentos se leen por mmap y nadie hace I/O con un lock tomado. El límite está en las escrituras: todas pasan por un solo writeMu, y dentro de él ocurre todo esto, una escritura detrás de otra:

Con claves y valores pequeños esto es rápido. Pero con valores grandes (calcular el CRC y copiar 100 KB), muchos núcleos, un disco NVMe que acepta escrituras en paralelo, o con Deferred/SYNC_ON_WRITE=false (donde ya no se espera el fsync), writeMu se vuelve el techo: un núcleo trabajando y el resto esperando.

3. Dos caminos posibles

Camino A: particionar (varios stores)

Repartir las claves en N stores independientes por hash(id) % N, cada uno con su writeMu, sus segmentos y su LSN. Es lo más simple: casi no hay código nuevo y escala casi lineal.

Pero rompe dos cosas: ya no hay un LSN global (cada partición cuenta el suyo, y la replicación tendría que llevar N posiciones), y Keys/ForEach ordenados tendrían que mezclar N listas. Cambia la API de replicación, que josefina y otros consumidores usan.

Camino B: un solo log con reserva de espacio (recomendado)

Mantener un log y un LSN, pero sacar del lock casi todo el trabajo: el lock solo sirve para reservar un LSN y un lugar en el archivo (unos nanosegundos), y cada escritor codifica y escribe en paralelo en su hueco. Es la técnica de los logs de bases de datos modernas (el Aether de Shore-MT, el log de InnoDB 8.0, el anillo de LMAX Disruptor).

RecomendaciónEl camino B: conserva la API, el formato y el LSN global, que es lo que hace útil al store para replicar. El resto del documento lo desarrolla. El camino A queda como plan de respaldo si B resultara demasiado complejo.

4. La idea: reservar, escribir, publicar

Cada escritura pasa por tres pasos. Solo el primero es serial:

Analogía: la fila del banco con turnosAl llegar tomas un turno numerado (reservar: instantáneo). Varios cajeros atienden a la vez (escribir en paralelo). Pero el tablero de "atendidos" solo avanza en orden: si el turno 9 sigue en caja, el 10 y el 11 esperan aunque ya terminaron (publicar en orden). Nadie se salta la fila del tablero, y aun así los cajeros nunca están ociosos.

5. Locks por clave: para que la semántica siga exacta

Como el modelo es id → []byte y cada operación toca un solo id, el único conflicto posible es entre escrituras del mismo id: no hay transacciones de varias claves que coordinar. Eso es lo que hace viable la concurrencia sin un lock global. Insert solo escribe si la clave no existe; Update solo si existe y el valor cambió. Esa comprobación y la escritura deben ser atómicas para la misma clave; para claves distintas, no importa.

Por eso writeMu se reemplaza por locks por clave (lock striping): un arreglo fijo de, por ejemplo, 1.024 mutex, y cada id usa el de hash(id) % 1024.

  • Dos escrituras de u1 toman el mismo mutex: se ordenan entre sí y la comprobación sigue siendo exacta.
  • Escrituras de u1 y u2 casi siempre toman mutex distintos y van en paralelo. Si chocan en el mismo (1 en 1.024), solo esperan un poco: es correcto igual.
  • El escritor sostiene su lock de clave hasta publicar. Así, para una misma clave, el orden del índice es el orden del LSN.
¿Por qué no un lock por cada clave en un mapa?Un map[string]*sync.Mutex crece sin límite y necesita su propio lock para insertar y limpiar entradas. Un arreglo fijo de mutex no ocupa memoria extra por clave y nunca se limpia. El precio es algún choque ocasional entre claves distintas, que es inofensivo.

6. La marca de agua: orden sin un lock grande

La marca de agua (watermark) es un número: el LSN más alto tal que todos los anteriores ya están escritos. Hay dos:

MarcaSignificaQuién la usa
publishedTodo LSN ≤ este está escrito en el archivo (aún quizá no en disco).Índice, hooks de Sync, límite visible de los lectores.
durableTodo LSN ≤ este ya pasó por fsync.El escritor retorna cuando durable ≥ su LSN (group commit, como hoy).

¿Cómo avanza published sin un lock grande? Cada escritor, al terminar su WriteAt, marca su LSN como hecho en un anillo de banderas atómicas (posición LSN % tamaño). Luego intenta avanzar la marca: mientras la bandera del siguiente LSN esté puesta, la limpia y suma uno. Quien logre avanzarla publica esos cambios en orden (índice y Sync) y despierta a los que esperaban.

Para no complicarlo de entrada, la primera versión puede hacer este avance bajo un publishMu pequeño: el trabajo pesado (CRC, copia, WriteAt) ya quedó fuera, y publicar es solo actualizar punteros en memoria.

7. El camino de escritura en Go (borrador)

Así quedaría Update. Los nombres siguen el estilo del paquete; es un borrador para discutir, no código compilado:

func (s *FileStore) update(id string, data []byte, wait bool) (bool, error) {
    if err := s.checkWrite(id); err != nil {
        return false, err
    }
    s.gate.RLock()                 // la compactación toma gate.Lock para detener a todos
    defer s.gate.RUnlock()

    mu := s.keyLock(id)            // &s.keyLocks[hash(id) % 1024]
    mu.Lock()
    defer mu.Unlock()              // se suelta después de publicar

    ref, exists := s.getIndex(id)
    if !exists {
        return false, nil
    }
    if !ref.differs(data) {        // igual que hoy: CRC primero, bytes si hace falta
        old, err := s.readPinned(ref, id)
        if err != nil {
            return false, err
        }
        if bytes.Equal(old, data) {
            return false, nil
        }
    }

    // ① Reservar: único paso serial, unos nanosegundos.
    res, err := s.reserve(recordSize(id, data))   // {lsn, seg, offset}
    if err != nil {
        return false, err
    }

    // ② Escribir en paralelo con los demás escritores.
    buf := encodeRecord(res.lsn, id, data, Active) // CRC + encabezado + datos
    if err := res.seg.writeAt(buf, res.offset); err != nil {
        s.abandon(res)                             // ver "Riesgos"
        return false, err
    }

    // ③ Publicar en orden y esperar la durabilidad.
    s.complete(res, Change{Op: OpUpdate, ID: id, Data: data, LSN: res.lsn},
        &recordRef{segment: res.seg.n, offset: res.offset, length: uint32(len(data)), crc: checksum(data), hasCRC: true})
    s.waitPublished(res.lsn)                       // ya está en el índice y Sync lo vio
    if wait && s.SyncOnWrite {
        return true, s.waitDurable(res.lsn)       // group commit, como hoy
    }
    return true, nil
}

Y la reserva, el único punto serial:

func (s *FileStore) reserve(size int64) (reservation, error) {
    s.reserveMu.Lock()
    defer s.reserveMu.Unlock()
    if s.tail+size > s.MaxSegment {
        if err := s.rotateLocked(); err != nil {   // ver "Rotación"
            return reservation{}, err
        }
    }
    r := reservation{lsn: s.WAL.inc(), seg: s.active, offset: s.tail}
    s.tail += size
    return r, nil
}
Orden de locks nuevocompactMu → gate → keyLock(id) → reserveMu → publishMu → indexMu → fragmentos. reserveMu y publishMu nunca se sostienen mientras se hace I/O ni mientras se espera a otro.

8. Simulador de la marca de agua

Llegan varias escrituras a la vez. Cada una reserva su LSN al instante (naranja), termina de escribir en un tiempo al azar (azul), y solo se publica (verde claro) cuando todas las anteriores terminaron. Después, un fsync compartido las vuelve durables (verde fuerte).

reservadaescrita, esperando turnopublicada (visible)durable (fsync)

Activa "una escritura muy lenta": verás cómo las de detrás terminan de escribir pero esperan su turno para publicarse. Ese es el costo del orden global, y la razón de abandonar con rapidez una escritura que falla (sección 12).

9. Lecturas más rápidas

Get ya es concurrente y no necesita cambios: el índice solo apunta a registros publicados, y los lectores leen hasta visible = offset de published. Las mejoras propuestas para lectura son otras:

9.1 Índice ordenado para Keys y ForEach

Hoy cada llamada ordena todas las claves (O(n log n)). Si cada fragmento del índice guardara además un árbol ordenado (por ejemplo un B-tree en memoria como github.com/google/btree, que tiene copias baratas copy-on-write), Keys(asc, offset, limit) recorrería solo lo pedido: Keys(true, 0, 10) costaría lo mismo con mil claves que con diez millones. Como el reparto en fragmentos es por hash, haría falta mezclar los 64 árboles con un heap, que solo toma los primeros offset + limit.

9.2 Lecturas sin lock (RCU)

Cada fragmento podría guardar su mapa detrás de un atomic.Pointer: los lectores lo cargan sin lock alguno y los escritores publican una versión nueva. Copiar un mapa entero en cada escritura es caro, así que conviene solo si las lecturas dominan por mucho; con el árbol copy-on-write del punto anterior la copia es parcial y barata.

9.3 Lecturas consistentes de varias claves

Con la marca de agua aparece algo nuevo gratis: un instante consistente. Un ForEach que anote published al empezar puede ignorar cualquier registro con LSN mayor, y así ve el store exactamente como estaba en ese LSN, aunque otros sigan escribiendo. Requiere guardar el LSN en el recordRef (8 bytes más por clave) y conservar la referencia anterior mientras haya lecturas abiertas, una forma simple de MVCC.

10. Rotación, compactación y cierre

  • Rotación: quien reserva y no cabe, crea el segmento nuevo dentro de reserveMu. El viejo no se sella (fsync + solo lectura) hasta que published alcanza su último LSN: puede haber escritores todavía escribiendo en él. Un contador de escrituras pendientes por segmento lo resuelve.
  • Compactación: sus fases 1 y 3 hoy toman writeMu para "congelar" el log. Con la propuesta toman gate.Lock(), que espera a que terminen las escrituras en curso y frena las nuevas. La fase 2, la lenta, sigue sin locks.
  • Close: toma gate.Lock(), espera published == WAL, hace fsync y retira los segmentos, como hoy.
  • Hooks de Sync: se llaman al publicar, en orden de LSN, bajo publishMu. Siguen debiendo ser rápidos y no escribir en el store.

11. ¿Sigue siendo seguro ante una caída?

Con escrituras en paralelo, un corte de luz puede dejar huecos: el registro 10 escrito, el 9 a medias. Al abrir, scan recorre el segmento y se detiene en el primer registro inválido (el 9), así que el 10 se pierde aunque esté completo. ¿Es un problema?

No, por la marca de aguaUn escritor solo retorna cuando durable ≥ su LSN, y durable nunca pasa un hueco. Si el 9 no terminó, el 10 nunca retornó true ni llegó a Sync: perderlo es correcto. Todo lo confirmado está antes del primer hueco. repairTail lleva el resto a cuarentena como hoy.

Un detalle: si el segmento se preasigna o el hueco queda en ceros, scan lee IDLen = 0 y se detiene por esa regla, que ya existe. No hace falta cambiar el formato ni la recuperación.

12. Riesgos y costos

Una escritura que falla bloquea a las siguientesSi el WriteAt del LSN 9 falla (disco lleno), su hueco nunca se llena y la marca de agua se detiene: todo lo posterior espera para siempre. Hay que abandonar el LSN: escribir en su hueco un registro de relleno válido (un tombstone de un id reservado como "\x00pad", que rebuildIndex ignore) y marcarlo hecho. Si ni eso se puede escribir, el store pasa a un estado de error permanente, como ya hace hoy segment.writeErr.
Más complejidadHoy la corrección se explica con "un escritor a la vez". La propuesta agrega reservas, dos marcas de agua, un anillo, locks por clave y una compuerta. Cada pieza es conocida, pero el conjunto es más difícil de razonar. Hay que acompañarla de pruebas con -race y de pruebas de caída (matar el proceso en mitad de escrituras y reabrir).
La ganancia depende de la cargaSi cada escritura espera su fsync y el disco es lento, el fsync manda y el group commit ya lo comparte: la mejora será modesta. La ganancia grande aparece con valores medianos o grandes, muchos núcleos, NVMe, Deferred o SYNC_ON_WRITE=false. Por eso hay que medir primero.

13. Plan por fases y cómo medirlo

  • Medir la línea base con go run ./test/storebench -d 30s -w 1000: escrituras/s, latencia p99 y uso de CPU, con valores de 100 B, 4 KB y 64 KB, con y sin SYNC_ON_WRITE. Si la CPU de un solo núcleo no es el techo, parar aquí.
  • Fase 1: sacar trabajo del lock sin cambiar la estructura. Calcular el CRC y armar el buffer antes de tomar writeMu (el registro solo necesita el LSN, que se escribe en los primeros 8 bytes al reservar). Es un cambio pequeño y seguro que ya reduce la sección serial.
  • Fase 2: locks por clave + reserva + marca de agua con publishMu simple. Pruebas: dos Insert del mismo id a la vez (exactamente un true), Sync recibe LSN 1…N sin huecos, matar el proceso a mitad y reabrir.
  • Fase 3: índice ordenado para Keys/ForEach, medido con 1 y 10 millones de claves.
  • Fase 4 (opcional): lecturas consistentes por LSN y publicación sin publishMu (anillo atómico), solo si las mediciones lo justifican.

Cada fase debe dejar el store compatible con los archivos existentes y actualizar la sección store/ de CLAUDE.md, el GoDoc, el README y doc/CHANGELOG.md, como pide el proyecto.
